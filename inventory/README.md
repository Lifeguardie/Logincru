# מערכת ספירת מלאי למסעדה

מחליפה את דפי הספירה המודפסים: סופרים בטלפון, הנתונים נשמרים בשרת,
ומקבלים שווי מלאי והיסטוריה שאפשר להשוות.

מערכת **עצמאית לחלוטין** — מסד נתונים משלה, משתמשים משלה, פורט משלה.
היא לא נוגעת בשום מערכת אחרת.

---

## יחידות מידה ותמחור

זו הנקודה החשובה במערכת. במסעדה יש שלושה מצבים שונים, וכולם עובדים:

| מצב | דוגמה | איך סופרים | איך מתומחר |
|---|---|---|---|
| מתומחר ונספר ביחידות | בקבוק בירה | 24 יחידות | 4.50 ₪ ליחידה |
| **מתומחר בקילו, נספר ביחידות** | שניצל קפוא | 40 יחידות | 45 ₪ לק"ג, יחידה = 0.180 ק"ג |
| מתומחר בקילו, נשקל | עגבניות | 12.4 ק"ג | 8 ₪ לק"ג |

### איך זה מוגדר

לכל פריט יש:

- **יחידת בסיס** (`kg` / `liter` / `unit`) — יחידת החישוב של הפריט
- **מחיר ליחידת בסיס** — אם יחידת הבסיס היא ק"ג, זה **המחיר לקילו**
- **יחידות ספירה** — כל דרך שבה מותר לספור את הפריט, עם **מקדם**:
  כמה יחידות בסיס יש ביחידת ספירה אחת

**דוגמה — שניצל:** יחידת בסיס `ק"ג`, מחיר `45 ₪`.

| יחידת ספירה | מקדם | כלומר |
|---|---|---|
| ק"ג | 1.0 | קילו אחד |
| יחידה | 0.180 | שניצל אחד שוקל 180 גרם |
| ארגז | 5.0 | ארגז שוקל 5 ק"ג |

ספירה של **2 ארגזים + 7 יחידות** = `2×5.0 + 7×0.180` = **11.26 ק"ג** = **506.70 ₪**.

### שלושה דברים שחשוב לדעת

1. **אפשר לספור אותו פריט בכמה יחידות באותו אזור.** בבר יש 3 בקבוקים
   סגורים ובקבוק פתוח ששוקל 400 גרם — שתי הזנות, פריט אחד, והמערכת
   מסכמת. במסך הספירה כל היחידות מוצגות זו לצד זו.

2. **כמויות עשרוניות מותרות בכל מקום.** "חצי ארגז" ו-2.4 ק"ג הם קלט תקין.

3. **משקל אריזה (טרה).** ליחידת שקילה אפשר להגדיר את משקל המיכל הריק,
   והמערכת מנכה אותו אוטומטית. בלי זה משקל הפלסטיק נספר כמלאי.

### מחירים היסטוריים

המקדם והמחיר נשמרים בשורת הספירה כתמונת מצב. **עדכון מחיר בקטלוג לא
משנה ספירות שכבר נסגרו** — ספירה מלפני חודשיים תמשיך להראות את השווי
שהיה נכון אז.

## התקנה

דרישות: Node.js 20 ומעלה, MariaDB 10.4 / MySQL 8 ומעלה.

```bash
cd inventory
npm install
cp .env.example .env
```

ערוך את `.env`:

```bash
# חובה להחליף - צור סוד אקראי:
openssl rand -hex 32
```

הרץ מיגרציות ונתוני התחלה:

```bash
npm run migrate          # יוצר את מסד הנתונים והטבלאות
npm run seed             # אזורים, מחלקות, ומשתמש מנהל
npm run seed -- --demo   # בנוסף: פריטי דוגמה שמדגימים את כל מצבי התמחור
```

ה-seed יוצר משתמש `admin` עם סיסמה `admin1234`. **המערכת תדרוש להחליף
אותה בהתחברות הראשונה** ולא תאפשר שום פעולה אחרת עד אז. אפשר לקבוע מראש:

```bash
SEED_ADMIN_USER=meir SEED_ADMIN_PASSWORD='...' npm run seed
```

בנה את הלקוח והפעל:

```bash
npm run build:client
npm start                          # פיתוח
pm2 start ecosystem.config.js      # פרודקשן
```

השרת מגיש גם את ה-API וגם את הממשק מאותו פורט (ברירת מחדל 4010).

**מאחורי nginx או reverse proxy אחר** יש לקבוע `TRUST_PROXY=1` ב-`.env`,
אחרת כתובות הלקוח ייראו כולן כמו ה-proxy. **בלי proxy** להשאיר `0` —
אחרת אפשר לזייף כתובת ולעקוף את מגביל ניסיונות ההתחברות.

### פיתוח עם רענון חי

```bash
npm run dev                     # שרת על 4010
npm --prefix client run dev     # לקוח על 5173, עם proxy ל-API
```

## שימוש

0. **הגדרות** (פעם אחת) — אזורי הספירה והמחלקות, ולכל אזור "סדר הדף":
   הפריטים מסודרים בדיוק כמו בדף הנייר, ומסך הספירה מציג אותם כך.
1. **פתיחת ספירה** — מנהל פותח ספירה חדשה (השם מתמלא לפי החודש). יכולה להיות
   ספירה פתוחה אחת בלבד; ספירה שנפתחה בטעות נמחקת מהדשבורד.
2. **ספירה** — כל סופר בוחר אזור ומזין כמויות, או מצלם את הדף. מסך אחד לכל אזור.
3. **סגירה** — מנהל סוגר (האישור מראה כמה פריטים עדיין לא נספרו), והשווי מקובע.
   אפשר לפתוח מחדש אם התגלתה טעות; ספירה סגורה לא נמחקת.
4. **רכש** — רושמים את הקניות שבין הספירות, ידנית או מאקסל של חשבונית.
5. **דוח צריכה** — `מלאי פתיחה + רכש − מלאי סגירה`. בחירה לפי חודש או בין כל
   שתי ספירות.

### דשבורד

מסך הבית מראה את הספירה הפתוחה וההתקדמות לפי אזור, ומתחתיה שני גרפים:
שווי המלאי לאורך הספירות הסגורות, ופילוח המחלקות של הספירה האחרונה.

### הרשאות

| תפקיד | מה מותר |
|---|---|
| `counter` | לצפות בקטלוג, ולהזין שורות ספירה |
| `manager` | בנוסף: קטלוג, מחירים, יחידות, פתיחה וסגירת ספירות, רכש, דוחות |
| `admin` | בנוסף: ניהול משתמשים (לשונית "משתמשים") |

סיסמה שמנהל קובע — ביצירת משתמש או באיפוס — היא זמנית: המשתמש חייב
להחליף אותה בהתחברות הבאה. השבתה, שינוי תפקיד ואיפוס תופסים מיד, גם על
מכשיר שכבר מחובר. אחרי 10 ניסיונות התחברות כושלים ל-15 דקות החשבון נחסם
זמנית מאותה כתובת (ו-30 מכל הכתובות יחד).

### צילום דף הספירה

במקום להקליד, מצלמים את הדף הכתוב ביד. האפליקציה שולחת את התמונה יחד עם
רשימת הפריטים של אותו אזור, ומקבלת בחזרה את השורות שזוהו: איזה פריט, כמה,
ובאיזו יחידה. ההתאמה נעשית מול הפריטים של האזור בלבד — טווח קטן, דיוק גבוה.

**שום ערך לא נכנס לספירה בלי אישור.** מסך האישור מציג את הצילום לצד כל
שורה שזוהתה, עם רמת ביטחון (ברור / לבדוק / ספק). כל שדה ניתן לתיקון —
פריט, כמות, יחידה — ושורה בלי התאמה לא מסומנת עד שמשייכים אותה ידנית.
כתב יד וכמויות זה בדיוק המקום שבו טעות שקטה עולה כסף.

הפעלה: מגדירים `ANTHROPIC_API_KEY` ב-`.env`. בלי המפתח כפתור הצילום מוסתר
וכל השאר עובד רגיל. ב-`.env` אפשר גם לשנות את המודל (`OCR_MODEL`) ואת רמת
המאמץ (`OCR_EFFORT` — `high` לקריאה מדויקת יותר של כתב יד, `medium` זול יותר).
התמונה מוקטנת בטלפון ל-1600px לפני השליחה, כדי לחסוך זמן העלאה ועלות.

### התקנה בטלפון

שתי דרכים:

**א. אפליקציית Android (APK)** — קישור הורדה קבוע:
`https://github.com/Lifeguardie/Logincru/releases/download/inventory-apk-latest/inventory.apk`

מורידים לטלפון, מאשרים התקנה ממקור לא ידוע, פותחים — ובפעם הראשונה מזינים את
**כתובת השרת** (למשל `https://inventory.example.com`). האפליקציה היא מעטפת:
הנתונים יושבים בשרת, לא בטלפון. את הכתובת אפשר לשנות ממסך ההתחברות.

ה-APK נבנה אוטומטית ב-GitHub Actions (`.github/workflows/android-apk.yml`) בכל
push שנוגע ב-`inventory/`, או ידנית מלשונית Actions. הוא חתום בחתימת debug —
מתאים להתקנה ישירה, לא ל-Play Store (שם נדרש keystore — שלב נפרד).

לפני HTTPS: ה-manifest מאפשר זמנית `http://` (`usesCleartextTraffic`) כדי לבדוק
מול `http://IP:4010`. **אחרי שיש דומיין עם תעודה — להסיר את זה** מ-
`client/android/app/src/main/AndroidManifest.xml`.

**ב. PWA** — פותחים את הכתובת בדפדפן הטלפון ובוחרים "הוסף למסך הבית".
נפתח במסך מלא עם אייקון, ונטען גם בלי רשת — נתוני המלאי עצמם לעולם לא
נשמרים במטמון, רק המעטפת.

### עבודה בלי קליטה

במחסן ובמקררים אין רשת. כל הזנה נשמרת קודם מקומית בטלפון ורק אחר כך
נשלחת, ונמחקת מהתור רק אחרי שהשרת אישר אותה. חיווי בתחתית המסך מראה
כמה הזנות עדיין ממתינות. אפשר לסגור את האפליקציה באמצע — ההזנות יישלחו
לבד ברגע שתהיה רשת.

## ייבוא מאקסל

הייבוא הוא תמיד דו-שלבי: קודם תצוגה מקדימה שמראה בדיוק מה ייווצר ומה
יעודכן, ורק אחרי אישור נכתב משהו.

המערכת מזהה כותרות בעברית ובאנגלית:

| שדה | כותרות מזוהות |
|---|---|
| שם פריט (חובה) | `שם פריט`, `שם`, `פריט`, `name` |
| מק"ט | `מק"ט`, `מקט`, `קוד`, `sku` |
| מחלקה | `מחלקה`, `קטגוריה`, `category` |
| יחידת מידה | `יחידת מידה`, `יחידה`, `base unit` |
| מחיר | `מחיר`, `מחיר לקילו`, `עלות`, `price` |
| ספק | `ספק`, `supplier` |
| אזור | `אזור`, `מיקום`, `location` |

מחירים מתקבלים גם עם סימן שקל ופסיקים. תאריכים ברכש מתקבלים בפורמט
`DD/MM/YYYY` וגם כתאריך אקסל.

### בדיקות

```bash
npm test                      # שרת: יחידות, זיהוי מצילום, ו-API מקצה לקצה
npm --prefix client test      # לקוח: תור השמירה
```

בדיקות ה-API (`server/tests/api.test.js`, `security.test.js`) מרימות את השרת
בתוך התהליך על מסדי נתונים ייעודיים (`resto_inventory_test*`) שנבנים מחדש
בכל ריצה, ומדברות איתו ב-HTTP אמיתי. אם אין MariaDB זמין הן מדלגות.

השרת: המרות בין יחידות, ניכוי טרה, כמויות עשרוניות, ערכים שמגיעים מה-DB
כמחרוזות, שגיאות עיגול של float; ואימות תשובות הזיהוי מצילום מול הקטלוג
(מזהה שהמודל המציא, יחידה לא קיימת, כמות שלילית, סירוב) עם לקוח מזויף.

הלקוח: הזנה שנכנסת לתור בזמן ששליחה קודמת באוויר לא נדרסת, ותיקון של
שדה בזמן שליחה לא נבלע — שני מקרים שנתפסו רק בהרצה בדפדפן אמיתי.

## פריסה על שרת (IP ופורט)

סקריפט אחד מתקין ומעדכן. הוא מבודד לחלוטין: מסד נתונים נפרד (`resto_inventory`) עם משתמש
שיש לו הרשאות רק עליו, תיקייה נפרדת (`~/resto-inventory`), פורט נפרד (4010) ותהליך PM2 נפרד.
הוא לא נוגע ב-nginx ולא בשום מערכת אחרת על השרת.

```bash
curl -fsSL https://raw.githubusercontent.com/Lifeguardie/Logincru/claude/restaurant-inventory-system-e8ptqa/inventory/deploy/install.sh | bash
```

מה הוא עושה: בודק Node 20+ ו-MariaDB (מתקין MariaDB אם חסר), מוריד את הקוד, יוצר מסד
ומשתמש עם סיסמה אקראית, כותב `.env` עם `JWT_SECRET` אקראי, בונה את הממשק, מריץ מיגרציות,
יוצר את משתמש המנהל, מפעיל ב-PM2, מוסיף גיבוי יומי ב-cron, ובודק שהשרת עונה.
בסוף הוא מדפיס את הכתובת להזנה בטלפון.

- **עדכון גרסה:** אותה פקודה שוב. קובץ `.env` והמסד נשמרים.
- **ב-AWS:** לפתוח TCP 4010 ב-Security Group (Inbound).
- **אפשרויות:** `PORT=4020`, `APP_DIR=/opt/inventory`, `DEMO=1` (פריטי דוגמה),
  `DB_ROOT_PASSWORD=...` אם root של MariaDB דורש סיסמה.
- **הסרה מלאה:** `bash ~/resto-inventory/repo/inventory/deploy/uninstall.sh` (שומר גיבוי אחרון ב-`$HOME`).
- **הפעלה אוטומטית אחרי אתחול:** אם PM2 הותקן עכשיו, פעם אחת `pm2 startup` ואז הפקודה שהוא מדפיס.

בשלב הזה התעבורה היא HTTP על IP. כשיהיה דומיין: nginx עם Let's Encrypt מול הפורט,
`TRUST_PROXY=1` ב-`.env`, ובאפליקציית Android להסיר `usesCleartextTraffic`.

## תפעול

- **לוגים:** `logs/inventory.log`, ובפרודקשן גם `pm2 logs inventory`
- **גיבוי:** `./server/scripts/backup.sh` — mysqldump דחוס עם תאריך לתיקיית
  `backups/`, שומר 30 אחרונים. לשים ב-cron יומי:
  `0 3 * * * /path/to/inventory/server/scripts/backup.sh`
- **שינוי סף החריגות:** `VARIANCE_ALERT_PERCENT` ב-`.env` (ברירת מחדל 25%)
